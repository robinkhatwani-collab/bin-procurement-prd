Problem Definition

Why multi-party project tracking fails without a unified agentic platform

Background

Organisations managing complex, multi-party projects — procurement cycles, card launches, regulatory workflows — coordinate across dozens of sequential and parallel steps involving multiple stakeholder groups. Without a unified platform, these projects live in disconnected tools: static Excel or Smartsheet files, siloed Jira boards, or scattered Confluence pages — with no cross-tool visibility, no dependency intelligence, and no automated risk detection.

Reference Example — BIN Procurement: Launching a new payment card requires procuring a Bank Identification Number (BIN) from the card network. This is a complex, multi-party process involving the Issuer, Network, Processor, and Embosser — 31 sequential and parallel steps spanning ~5 months, currently managed in a static Excel file with no automation.

Solution Definition

A multi-agent web application — four specialised AI agents collaborating over a shared project data layer

Product Vision

An AI-Powered Multi-Project Tracker built as a web application. Users upload an Excel sheet and Agent 1 instantly generates a live HTML Status Tracker page. Three additional agents — a chatbot (Agent 2), a deadline monitor (Agent 3), and a dependency evaluator (Agent 4) — run continuously over all tracked projects.

POC Scope
In the POC phase, HTML pages and authentication are managed by the user locally. No backend database is required. Excel is the data source. The future phase replaces Excel with Smartsheet via live API and adds a proper database and auth layer.

High-Level Architecture

Knowledge Graph as Dependency Layer
Agent 4's dependency model is a direct application of the Knowledge Graph pattern: steps are nodes, dependency relationships are typed edges, and critical path detection is graph traversal. This is exactly how a Knowledge Graph enables multi-hop reasoning — applied to project risk.

Applied AI Techniques

How every major product decision maps to a specific, deliberate AI technique — grouped by capability area

Capability · Foundations
Foundations — Tokens, Transformers & RAG
▸Tokens & Context Windows — Agent 2's prompt budget is designed around Claude's 200K window. Project snapshots are compressed to JSON to stay under token limits.
▸RAG Architecture — Agent 2 uses RAG: project HTML pages are chunked, embedded, and retrieved before answering natural language queries. Never answers from training data.
▸Grounding — All four agent system prompts enforce strict grounding: answer only from provided project data. "I don't have that information" is a required fallback.
▸Encoder/Decoder Understanding — Chose Claude (decoder-only) for generation tasks. Encoder-style embeddings used for semantic search in Agent 2's retrieval layer.
Capability · Context & Retrieval
Context Management & Agentic RAG
▸Agentic RAG — Agent 2 decomposes multi-project queries, plans multi-step retrieval tool calls, evaluates result quality, and loops — rather than a single-shot retrieval. Matches the Agentic RAG loop pattern.
▸Context Management (Good Design) — Agent 2 uses structured context objects (project JSON snapshots) rather than raw HTML dumps. Avoids "lost-in-the-middle" by keeping context lean and structured.
▸Context Types — Short-term: conversation history. Structured: project JSON. Unstructured: HTML tracker pages. Each type handled differently in the retrieval pipeline.
▸In-Context Learning — Agent 3 email prompts use few-shot examples of good vs. bad reminder tone to guide the LLM without fine-tuning.
Capability · Agentic AI & Governance
Agentic AI, Evaluation & Responsible AI
▸Knowledge Graph → Agent 4 — Steps = nodes, dependencies = edges. Agent 4 traverses this graph to find critical path, blocked nodes, and cascade risks.
▸Perceive→Plan→Act Loop → Agent 3 — Observe (read deadlines) → Reason (classify urgency) → Act (send email). This is the agentic loop applied to project monitoring.
▸HHH Framework → Agent 3 guardrails — Helpful: timely alerts. Honest: only real data. Harmless: no blame language, never escalates without PM review.
▸Precision & Recall → Agent 4 metrics — P≥0.80 / R≥0.75 targets for cascade risk detection. F1 balance chosen deliberately — false negatives (missed risks) cost more than false positives.
▸Prompt Caching → Agent 2 cost — Repeated project context (scheme rules, dependency graph) is cached. Estimated 70–90% cost reduction on repeated multi-project queries.

Multi-Agent Architecture

Four specialised AI agents collaborating over a shared project data layer

Architecture Pattern — Orchestrator-Worker × Blackboard
A lightweight orchestrator routes each user goal to the right specialist agent (Orchestrator-Worker). The agents never message each other directly — they read from and write to a single shared project data layer, reacting to its current state (Blackboard). This combination gives the product three properties a single agent can't deliver: specialisation, parallelism, and a single source of truth.

Why Multi-Agent — not a single agent?

Single-Agent LimitationHow This System Solves It
Context window fills up across many projectsEach agent handles only its slice of the project data, keeping its context lean
One agent can't specialise in everythingA dedicated agent per job — generation, Q&A, monitoring, dependency analysis
Serial bottleneck — one task at a timeAgents 2, 3 and 4 run in parallel over all tracked projects
Hard to debug one long traceEach agent's output is isolated and independently inspectable

Memory Model — Shared vs Private

Reason Privately, Publish Publicly
Each agent reasons in its own private context (its task prompt, retrieved chunks, and intermediate steps) to stay focused and cost-efficient. It then writes only the distilled result — a generated tracker, an answer, a risk score, an email decision — to the shared project data layer, which is the single source of truth every other agent builds on. Sensitive data (DRI emails, PII) is scoped to the agent that needs it, never broadcast into shared memory unnecessarily.

Agent Specifications

Four specialised AI agents — each designed around a specific, deliberate AI technique

1Source Configurator & Tracker Generator
Tokens Grounding

Trigger: User uploads Excel file via web UI.

  • Validates schema (required columns A–H present)
  • Parses all steps, DRI names, emails, dates, statuses, dependencies
  • Computes RAG status, % complete, overdue count
  • Generates a self-contained HTML Status Tracker page
  • Adds project card to the central dashboard with a live link
  • Flags security steps (Column J = Y) — AI monitoring disabled

Agentic behaviour: Schema validation with intelligent error messaging. Adaptive layout — card view under 10 steps, table view for 10+.

Output: project-{slug}.html added to dashboard.

2Project Intelligence Chatbot
RAG Grounding Agentic RAG Context Management Prompt Caching n8n Orchestration

Trigger: User types a natural language question in the chat panel.

  • Has read access to all project HTML tracker pages (RAG retrieval layer)
  • Decomposes complex queries into multi-step retrieval plans — Agentic RAG pattern
  • Maintains structured context state across turns — not raw conversation history
  • Supports: "Which projects are at risk?", "Who owns the blocked step in Project X?"
  • Strictly grounded — never extrapolates beyond project data (Grounding)
  • Prompt caching applied to repeated project context — reduces query cost by ~70%
  • Out-of-scope questions (e.g. general advice) rejected before any LLM call — Scope Guard node

Implementation (POC): Orchestrated by an n8n workflow running locally. The chat panel POSTs to an n8n Webhook → n8n fetches live tracker HTML → Scope Guard IF node filters off-topic questions → Claude Sonnet called via Anthropic API → answer returned to UI. See Section 12 for the full node-by-node spec.

Agentic behaviour: Plans a sequence of n8n tool calls to answer complex queries. Does not answer in one static prompt — decomposes the question first. (Agentic RAG loop)

3Progress Monitor & Email Notifier PLANNED
In-Context Learning Perceive→Plan→Act HHH Framework

Trigger: Scheduled run (nightly) or on-demand by PM.

  • Observe: reads all project Excel files, compares estimated end dates to today (Perceive)
  • Reason: classifies urgency — overdue / 3-day warning / 7-day heads-up (Plan)
  • Act: generates personalised DRI email, sends, logs (Act)
  • HHH guardrails: Helpful (timely), Honest (data-only), Harmless (no blame language)
  • Security flag respected — never emails about flagged steps without PM approval

Agentic behaviour: Observe → Reason → Act loop. This is the core agentic pattern from Agentic Skills applied directly to project monitoring.

4Dependency Evaluator & Milestone Planner PLANNED
Knowledge Graph SMART Goals Precision & Recall Agent Metrics

Trigger: On project load and after each status update.

  • Knowledge Graph traversal: Column I dependency data → nodes + edges → critical path (Knowledge Graph)
  • Identifies all steps currently blocked by incomplete upstream steps
  • Detects cascade risk — if Step N delayed, which downstream steps are at risk?
  • Milestone recommendations follow SMART criteria: specific, measurable, time-bound (SMART Goals)
  • Cascade risk target: P≥0.80, R≥0.75 — recall prioritised over precision (Precision/Recall)

Agentic behaviour: Multi-step planning — reads graph, traverses chain, computes critical path, outputs prioritised action plan. Memory: retains prior milestone suggestions to detect regressions.

Precision vs Recall Trade-off Decision (Agent 4)
For cascade risk detection, we deliberately bias toward Recall (R≥0.75) over Precision. A false negative (missed cascade risk) causes a real project delay. A false positive (unnecessary alert) costs a PM 5 minutes of review. This is a direct application of the Precision/Recall trade-off — the business cost asymmetry determines the dial setting.

Prompt Strategy

Structured, auditable prompts — built on Grounding, Context Management, and the HHH Framework

Design Principles

Grounded — always use real project data, never hallucinate. Scoped — structured context objects, not raw document dumps. HHH-Aligned — every prompt enforces Helpful, Honest, Harmless. Auditable — every AI output logged with its input context.

Agent 2 — Project Chatbot RAGAgentic RAG

SYSTEM: You are a helpful project assistant with read access to all projects tracked on the Multi-Project Tracker platform. You will be given live project data as JSON context. Answer only based on the provided data. If information is not in the data, say "I don't have that information." Never guess or extrapolate. Keep answers under 3 sentences unless the user asks for a list. You may query multiple projects to answer a question — plan your tool calls before responding. USER: [Project data snapshots: {{project_snapshots_json}}] User question: {{user_question}}

Agent 3 — DRI Deadline Alert Email HHH — Helpful, Honest, Harmless

SYSTEM: You are a professional project coordinator. Write a brief, friendly, and professional reminder email to a stakeholder about an overdue or upcoming project step. Keep it under 100 words. Do not use blame language (Harmless). Be specific about the step, deadline, and the downstream impact of the delay (Helpful + Honest). Sign off with the PM's name. USER: Recipient: {{dri_name}} ({{dri_email}}) Project: {{project_name}} Step: {{step_number}} — {{step_description}} Was Due: {{estimated_end_date}} | Days Overdue: {{days_overdue}} Next Dependent Step: {{next_step}} (owned by {{next_dri_name}}) PM Name: {{pm_name}} Write the email body only. No subject line.

Agent 4 — Dependency Risk & Milestone Planner Knowledge GraphSMART Goals

SYSTEM: You are a senior project risk analyst specialising in dependency management. Analyse the provided project dependency graph and current step statuses. Identify all blocked steps, cascade risks, and the critical path. Then recommend the next 3–5 milestones the team should prioritise — each milestone must be SMART: Specific, Measurable, Achievable, Relevant, Time-bound. Be concise, data-driven, and actionable. Output as JSON. USER: Project: {{project_name}} | Target Launch: {{launch_date}} | Today: {{today}} Step Statuses: {{step_statuses_json}} Dependency Graph: {{dependency_graph_json}} Provide: (1) blocked_steps, (2) cascade_risks with impact, (3) critical_path, (4) recommended_milestones (SMART), (5) overall_risk_score 0–100.

Agent 2 — n8n Workflow Specification

n8n as the orchestration backbone for the Project Intelligence Chatbot — local, webhook-driven, Claude-powered

How it works
n8n runs locally alongside the Python server (port 8080). The chat panel sends a POST to an n8n Webhook node; n8n fetches live tracker HTML, enforces a Scope Guard, calls Claude Sonnet via the Anthropic API, and returns a grounded answer — all without a separate backend service or database.

Workflow Nodes (in order)

#Node TypeNode NamePurposeKey Config
1WebhookChat ReceiverReceives POST from the chat panel UIMethod: POST · Path: /chat · Response mode: Last node · Body fields: message, conversation_id, history[]
2SetExtract FieldsMaps incoming JSON to clean variablesuser_message ← body.message · history ← body.history · conv_id ← body.conversation_id
3IFScope GuardRejects out-of-scope questions before any LLM call is madeTrue branch (in scope): message contains project / step / status / overdue / DRI / milestone / blocked / tracker · False branch → Node 4a
4aRespond to WebhookOut-of-Scope ReplyReturns boundary message immediately; no LLM calledBody: { "reply": "I can only answer questions about project status, steps, DRIs, and timelines." }
4bHTTP RequestFetch Tracker HTMLPulls the live tracker page from the local serverMethod: GET · URL: http://localhost:8080/bin-tracker · Output: raw HTML string. For multi-project: loop over project-index.json URLs.
5CodeParse Tracker HTMLExtracts structured project data from raw HTMLJS: parse step rows (number, description, DRI, status, dates), RAG status, overdue count · Output: project_context_json string
6CodeBuild Prompt ContextAssembles the full LLM input from project data + conversation historyCombines project_context_json + history[] into a structured context string · Tags repeated project data with Anthropic prompt cache marker to reduce cost ~70%
7HTTP RequestClaude API CallSends context + user question to Claude SonnetPOST https://api.anthropic.com/v1/messages · Header: x-api-key: {{ANTHROPIC_API_KEY}} · Model: claude-sonnet-4-6 · Max tokens: 300 · System prompt: see below
8CodeFormat ResponseExtracts clean answer text from Claude's API response enveloperesponse.content[0].text · Appends sources: ["tracker.html"] and timestamp

System Prompt (Node 7)

SYSTEM: You are a project assistant for the AI PM Tool. You have read access to live project tracker data provided as JSON context below. Answer ONLY based on the data provided. If information is not in the data, say "I don't have that information in the current tracker." Never guess, extrapolate, or fabricate step data. Keep answers under 3 sentences unless the user explicitly asks for a list. You may query multiple projects to answer a question — plan before you respond. Scope: you only answer questions about project status, step status, DRI assignments, overdue steps, dependency relationships, milestones, and project timelines. Politely decline anything outside this scope. USER: Project context: {{project_context_json}} Conversation history: {{history}} Question: {{user_message}}

Allowed (True branch)Blocked (False branch → immediate refusal)

DRI assignments — who owns which step
Dependency relationships — what's blocking what
Milestone recommendations from Agent 4

Questions about tools outside this project

Security-flagged steps (Column J = Y) — excluded from context entirely
PII beyond DRI name and email
Anything not present in the loaded project index

POC Limitation
Agent 2 reads from the generated HTML snapshot of the tracker. If the source Excel is updated, the tracker page must be re-generated (Agent 1 re-run) before the chatbot reflects the new data. A "Re-index" button in the chat panel triggers a fresh HTML fetch without reloading the page.
