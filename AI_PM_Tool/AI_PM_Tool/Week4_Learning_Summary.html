What is a Multi-Agent System?

A Multi-Agent system is a setup where multiple AI agents work together to complete a complex task — each agent handling a specific piece, rather than one agent doing everything.

🏢 The Company Analogy
Think of it like a company: the CEO (orchestrator) doesn't do all the work — they delegate to specialists. Each specialist (sub-agent) does one job well, and the CEO synthesises everyone's output into the final result.

The key insight is that multi-agent isn't just "more agents" — it's about separation of concerns, parallelism, and specialisation. Each agent does one thing well, and the orchestrator makes them work as a coordinated system.

🏗️
Topic 2 of 10
Core Architecture

Every multi-agent system is built from four core building blocks. Together they let independent agents collaborate without ever talking to each other directly.

🧠 Orchestrator Agent
The "brain." It receives the user's goal, breaks it into subtasks, assigns them to the right agents, and synthesises the final output.
👷 Sub-Agents
Specialised workers. Each has a narrow job (research, code, writing, analysis…) and the tools needed for it. They don't know about each other — they just receive a task and return a result.
🔧 Tools
What agents act on: web search, file systems, browsers, databases, code execution, APIs. Tools are what give agents real-world capability.
🗂️ Shared Memory / Context Store
A shared scratchpad. Agents write their intermediate results here; the orchestrator reads it to synthesise everything. This is how agents "collaborate" without directly talking to each other.
Orchestrator → Sub-Agents → Tools
The orchestrator delegates to sub-agents, each wired to its own tools; everyone reads & writes the shared memory.
🧠
Topic 3 of 10
Memory in Multi-Agent Systems — Shared vs Own

In a multi-agent system, memory comes in two layers. Each agent has its own (private) memory — its personal working context — and the system has a shared memory that everyone reads from and writes to. Getting the split right is what makes agents both focused and collaborative.

🔒 Own / Private Memory
Each agent's personal scratchpad — its task instructions, reasoning, and intermediate thinking. Invisible to other agents. Keeps each agent's context lean and focused, with no cross-talk noise.
🗂️ Shared Memory
A common store (context store / blackboard) that all agents and the orchestrator can access. Holds the task state and the distilled results agents publish. This is how agents collaborate without talking directly.
How Memory Flows
Each agent reasons in its own private memory, then publishes only the result to shared memory. The orchestrator reads shared memory to synthesise.

The two layers are easiest to compare side by side:

Dimension🔒 Own / Private Memory🗂️ Shared Memory
ScopeOne agent onlyAll agents + the orchestrator
HoldsTask prompt, reasoning, scratch workTask state & the distilled results agents publish
VisibilityInvisible to peersReadable by everyone
BenefitLean context, focus, no cross-talk noiseCollaboration & a single source of truth
RiskResults are lost unless written outCan bloat; needs write discipline & consistency
Use it forAn agent's internal thinkingHanding results between agents
🔑 The Golden Pattern
Agents reason privately, publish publicly. Keep each agent's raw thinking in its own memory to stay focused and cheap — then write only the clean, distilled result to shared memory so others can build on it. Dumping everything into shared memory bloats context and confuses every agent.
💡 PM Tip — Persistence & Privacy
Decide early what lives where: short-term working memory (per agent), shared task memory (this run), and long-term memory (a database / vector store that persists across sessions). And remember — if PII enters shared memory, every agent and tool can see it. Scope sensitive data to private memory.

Topic 4 of 10
Why Multi-Agent over Single Agent?

A single agent is simpler, but it hits walls as tasks grow. Multi-agent design exists to solve four specific limitations of the single-agent approach.

Problem with Single Agent How Multi-Agent Solves It
Context window fills up on long tasksEach agent handles a chunk, keeping its own context lean
One agent can't specialise in everythingDedicated agents per domain, each expert at one thing
Serial bottleneck — one step at a timeAgents can run in parallel, cutting wall-clock time
Hard to debug a single long traceEach agent's output is isolated and inspectable
💡 PM Tip
Don't reach for multi-agent by default — it adds orchestration cost and failure modes. Use it when you genuinely need specialisation, parallelism, or long-context relief. If a single well-prompted agent meets the requirement, ship that first.

Topic 5 of 10
Common Patterns

Four collaboration patterns show up again and again. They describe how agents are wired together.

Orchestrator → Workers most common
One controller, many executors. The orchestrator fans work out and synthesises the results.
Pipeline
Agent A → Agent B → Agent C, each passing its output to the next (e.g., research → draft → review).
Peer-to-Peer
Agents message each other directly — useful for debate/critique loops (one writes, another critiques, repeat).
Hierarchical
Orchestrators can themselves be sub-agents of a higher-level orchestrator — for very complex workflows.
🗺️
Topic 6 of 10
The 6 Architecture Types — When to Use Each

There are six main types of multi-agent architecture. Here is the mental model for choosing between them.

Type Use it when…
Orchestrator-WorkerYou have parallel, independent subtasks — the most common pattern in production AI systems.
PipelineSteps are strictly sequential and each stage transforms the output of the last (like an assembly line).
HierarchicalThe problem is so large it needs multiple layers of managers — each orchestrator is itself a worker for the level above.
Peer-to-PeerAgents need to negotiate or react to each other dynamically, with no natural "boss" agent.
Debate / CritiqueOutput quality is paramount — a proposer generates, a critic tears it apart, repeat until it's good. Great for writing, legal, and code review.
BlackboardAgents are event-driven — they don't talk directly, they read/write a shared store and react to changes.
🔑 The Real-World Truth
Most real systems combine patterns — e.g., a hierarchical structure where leaf agents run debate loops, and everyone writes to a blackboard. The patterns are building blocks, not strict either/or choices.

Single vs Multi-Agent — Decision Criteria & Case Studies

Multi-agent is powerful but not free — it adds orchestration cost, latency, and new failure modes. Before adding agents, run the task through these criteria.

① Decision Criteria
CriterionLean Single AgentLean Multi-Agent
Task shapeStraight line — one step after anotherTree / fan-out — branches & parallel paths
Latency budgetTight, real-time (e.g. <200ms)Relaxed — seconds are acceptable
ParallelismSteps are inherently sequentialIndependent subtasks can run at once
SpecialisationOne domain, one skillCross-domain expertise needed
Context sizeEverything fits in one context windowLong task — context would overflow
Cost & complexityKeep it cheap and simpleSpeed / quality gain justifies overhead
ObservabilityA single trace is easy to followNeed isolated, inspectable per-agent output
🧪 The Simplest Test
Draw the task as a flowchart. If it's a straight line → Single Agent. If it's a tree or fan-out → Multi-Agent.
② Credit Card Processing — Case Studies

Rule of thumb for this domain: Single agent when the task is real-time and latency-bound; Multi-agent when it's cross-domain and parallelism helps. Click each case to expand.

Single Transaction Authorization
Scenario: A card is tapped at a terminal; approve or decline within a ~200ms budget.
Why single: One tool call (limit / risk check), one decision, a hard latency ceiling. There is simply no time to spin up and coordinate multiple agents.
Pattern: Single agent → one tool → done.
Single Balance & Account Inquiry
Scenario: "What's my available credit?" / "When is my payment due?" in an app or IVR.
Why single: A straight-line lookup against one system of record, returned conversationally. No specialisation or parallelism to gain.
Pattern: Single agent with a read-only account tool.
Single Statement Summarisation
Scenario: Summarise a monthly statement — top merchants, spend by category, due amount.
Why single: One input (the statement), one output (the summary). It all fits in a single context window; adding agents only adds latency.
Pattern: Single agent, one summarisation pass.
Multi Fraud Detection
Scenario: On a suspicious transaction, five signals must be evaluated at once — velocity, geo-location, merchant risk, device fingerprint, and spend-pattern anomaly.
Why multi: The signals are independent, so they fan out and run in parallel; specialised agents score each far better than one generalist. Speed (parallelism) and quality (specialisation) both win.
Pattern: Orchestrator-Worker (or Blackboard) — workers score signals concurrently, the orchestrator fuses them into a risk decision.
Multi Dispute / Chargeback Resolution
Scenario: A cardholder disputes a charge; the case must pass compliance checks, a decision, and a customer-facing resolution letter.
Why multi: The work is a strict sequence where each stage transforms the last, and each stage needs different expertise (regulatory vs. adjudication vs. writing).
Pattern: Pipeline — Compliance → Decision → Resolution Letter.
Multi Credit Card Application Processing
Scenario: A new application must clear KYC (identity), a credit-bureau pull, and AML screening before approval.
Why multi: The three checks are independent and slow — running them in parallel cuts wall-clock time dramatically, and each is its own specialised domain.
Pattern: Orchestrator-Worker — KYC, Credit Bureau, and AML agents run in parallel; the orchestrator combines verdicts into an approve / decline.
🧭 The One-Liner
Single = real-time, latency-bound, one tool call (auth, balance, summary). Multi = cross-domain with parallelism (fraud's 5 signals, dispute's pipeline, application's KYC + bureau + AML). Straight line → single; tree → multi.

What is the OpenAPI Specification (OAS)?
📘 Definition
The OpenAPI Specification (formerly Swagger) is a standard, language-agnostic format for describing REST APIs. It's a JSON or YAML file that defines everything about an API — its endpoints, request/response formats, authentication, parameters, and data schemas.

Think of it as a contract between an API provider and its consumers: anyone — or any tool — can read the spec and know exactly how to use the API, without reading source code or docs.

A basic OAS file looks like this:

openapi: 3.0.0 info: title: My API version: 1.0.0 paths: /users/{id}: get: summary: Get a user parameters: - name: id in: path required: true schema: type: integer responses: '200': description: A user object
How OAS is Used
📑 Documentation — Swagger UI / Redoc auto-generate interactive docs from the spec; developers browse and test endpoints in the browser.
⚙️ Code generation — Tools like openapi-generator scaffold client SDKs and server stubs, so you don't write boilerplate by hand.
✅ Validation — Middleware validates incoming requests and outgoing responses against the spec at runtime, catching contract violations early.
🧪 Mocking — Tools like Prism spin up a mock server from the spec, so frontend teams build before the backend is ready.
🔬 Testing — Tools like Schemathesis auto-generate test cases by fuzzing every defined endpoint against the spec.
🚪 API gateways — AWS API Gateway, Kong and others import an OAS file to configure routing, auth, and rate limiting automatically.
🤖 AI / LLM tool use — LLMs (including Claude) read an OAS file to understand an API's capabilities and call it correctly — increasingly common in agent workflows.
📌 Current Version
The current version is OAS 3.1, which aligns fully with JSON Schema. The spec lives at spec.openapis.org.
🤖
Topic 10 of 13
How AI Models Use OAS

AI models interact with OAS in several distinct ways — from simply understanding an API to autonomously calling it inside an agent loop.

1 · Tool / Function Calling most common
The OAS is the "manual" the model reads to know what tools exist and how to call them. It picks an endpoint, constructs a valid request, gets the response, and synthesises an answer. This is how Claude tool use, OpenAI Assistants, and LangChain agents operate.
2 · Agentic Workflows
OAS lets an agent discover what an API can do and chain multiple calls without hard-coding each step — e.g., GET /customers?sort=revenue → get the ID → POST /emails. LangChain, LlamaIndex, and AutoGen have native OAS loaders.
3 · OAS → Structured Tool Schema
Claude and GPT-4 require tools in a specific JSON-schema format. OAS is the upstream source that gets converted into that format (libraries like openapi-llm, or custom parsers, do it automatically).
4 · RAG over API Documentation
For APIs with hundreds of endpoints, teams chunk the spec into a vector DB and retrieve only the relevant endpoint at query time — instead of stuffing the whole spec into context.
5 · Code Generation
Paste an OAS and ask "write a Python client for this API" — the model reads the schemas, params, and auth and generates accurate, typed code, avoiding hallucinated endpoints or wrong parameter types.
6 · Validation & Self-Correction
Some agents pass the OAS back to the model after it drafts a request, asking it to validate against the spec before sending — catching missing required fields or wrong params before they hit the real API.
The Core Pattern
📄 OAS File
↓
Parse into tool definitions
↓
Inject into model context (system prompt / tool list)
↓
Model reasons over available tools
↓
Constructs a valid API call
↓
Executes → response → reasons → continues ↻

Topic 11 of 13
What is MCP (Model Context Protocol)?
📘 Definition
MCP (Model Context Protocol) is an open standard introduced by Anthropic in late 2024 that defines how AI models communicate with external tools, data sources, and services. Think of it as a universal plug-and-socket system for AI integrations — the same way USB-C standardised device connections.

Before MCP, integrating LLMs with external APIs required feeding OpenAPI specs as text into the model's prompt and hoping the model correctly inferred how to call the API. MCP replaces this pattern with a native, structured protocol.

The Problem Before MCP
1. Write an OpenAPI spec describing your API endpoints
2. Feed that spec to the LLM as context (as raw text)
3. LLM guesses how to construct HTTP requests — handles auth, state, errors via prompt engineering
4. Parse the response and feed it back to the LLM
MCP's Three Core Primitives
🔧 Tools
Functions the AI can invoke — e.g., search_files, create_task, send_email. The AI calls these directly through structured JSON messages.
📂 Resources
Data the AI can read — e.g., documents, database records, file contents. Exposed as structured data at runtime.
💬 Prompts
Reusable prompt templates the server can provide to the AI host — standardising how common tasks are framed.
🔑 Key Insight
MCP is quickly becoming the de facto standard — GitHub, Slack, Google Drive, Postgres, and hundreds more now have MCP servers. It's to AI agents what REST was to web services: a common lingua franca that makes the ecosystem composable.

Topic 12 of 13
MCP vs OpenAPI Spec — How They Differ & Relate

MCP did not replace OpenAPI — it replaced the pattern of feeding OAS specs into LLM prompts. They operate at different layers and complement each other.

Aspect OpenAPI Spec MCP
Purpose Describe HTTP REST APIs for humans & machines Connect AI models to tools/services natively
Consumption LLM reads the spec as text, infers how to call it LLM uses a structured protocol with defined message types
Interaction model Stateless HTTP request/response Stateful, bidirectional sessions
Discovery Static doc at build time Dynamic — tools expose themselves at runtime
Auth / Context LLM must handle via prompting Built into the protocol layer
Error handling LLM interprets error text Structured error types the model understands natively
Architecture — How They Stack Together
🤖 LLM (Claude / GPT)
↕ structured tool calls
🏠 MCP Host (Claude.ai / VS Code / API)
↕ MCP protocol (JSON-RPC)
⚙️ MCP Server (one per service)
↕ uses at build time
🔧 Connector (auth, retries, rate limits)
↕ internalized
📄 OpenAPI Spec (what endpoints exist, params, auth)
↓ HTTP requests
🌐 REST API (GitHub, Slack, Google Drive…)
📌 The Key Insight
OpenAPI Spec solves "what can this API do?" at build time. MCP solves "how does an AI invoke it?" at runtime. The spec is never fed to the LLM as text — the Connector already internalized it. They operate at different layers and complement each other.

Topic 13 of 13
How Claude Selects Between Competing MCP Servers

When multiple MCP servers could handle the same task (e.g., "find my files" → Google Drive MCP, Dropbox MCP, or local filesystem MCP), Claude uses a structured selection process — not a random pick.

Selection Rules (in priority order)
1 · Explicit user mention — highest priority
"Find my Q3 report in Drive" → immediately routes to Google Drive MCP. Named service is a hard override signal.
2 · Tool name + description semantic matching
Every MCP tool has a name and description. Claude reads these like a semantic index — "find my Q3 report" matches against all available tool descriptions and the closest wins.
3 · Specificity wins over generality
"Search Google Drive spreadsheets and documents" scores higher than "Search files" — the specific tool signals it was built exactly for this case.
4 · Recency / last-used as tiebreaker
If you used Dropbox MCP five messages ago, it gets a slight bump in ranking when two tools otherwise tie.
5 · True tie → surface options to the user
When Drive and Dropbox both score equally, Claude doesn't pick silently — it asks the user to choose. This protects user autonomy; Claude won't silently pick your cloud storage provider.
Concrete Example — "Find My Files"
Three competing MCPs available:
☁️ Google Drive MCP
📦 Dropbox MCP
💻 Local Filesystem MCP
User says: "Find my Q3 report" (no service mentioned) → semantic match runs → all three score similarly → Claude asks: "I found matching tools in Google Drive, Dropbox, and local files. Which would you like to search?"
User says: "Find my Q3 report in Drive" → explicit mention → Google Drive MCP selected immediately, no ranking needed.
💡 PM Tip
When building products with MCP, tool descriptions are your ranking signal. Write them specifically — describe the exact service, file types, and use cases. Vague descriptions like "search files" will lose to specific ones in multi-MCP environments.
💳 Phase 5 — MCP in Practice: Credit Card Processing Case Studies

Case Study 1 of 4
Real-Time Fraud Detection
📋 Scenario
A customer swipes their card at a petrol station in Mumbai at 2 AM. Three seconds later, the same card is used at a mall in Dubai. The bank's AI agent must detect this anomaly and block the second transaction — all within 200ms.
MCP Servers Involved
transaction-history-mcp
Tool: get_last_transactions(card_id, limit) — fetches last N transactions with timestamps and geolocation
geolocation-mcp
Tool: calculate_travel_time(loc_a, loc_b) — returns minimum travel time between two locations
card-control-mcp
Tool: block_transaction(txn_id, reason) / flag_for_review(card_id)
How the AI Agent Executes This
1
New transaction arrives: Card #4532 — Dubai Mall — $340 — 02:03 AM
2
Calls get_last_transactions("4532", 5) → last txn was Mumbai petrol station at 01:58 AM (5 mins ago)
3
Calls calculate_travel_time("Mumbai", "Dubai") → minimum 3 hours by flight
4
Agent reasons: 5 min gap vs 3 hr minimum travel = impossible. Fraud detected.
5
Calls block_transaction("TXN-DXB-9821", "impossible_geolocation") + flag_for_review("4532") → SMS alert sent to customer
✅ Why MCP Makes This Better
Without MCP, the agent would need to read OpenAPI specs for each service, construct raw HTTP requests, and handle auth for each. With MCP, it calls block_transaction() like a function — the MCP server handles auth, retries, and the underlying Visa/Mastercard network API calls.

Automated Dispute Resolution

Calls send_sms() + send_email() → customer receives: "Dispute raised. Provisional credit of ₹8,500 added to your account within 24 hours."

OAS is how models call APIs reliably. It's the interface layer between LLM reasoning and typed APIs — parsed into tool schemas, injected into context, so the model picks the right endpoint and builds a valid call instead of guessing.
11
MCP is the runtime protocol for AI ↔ tool communication. Introduced by Anthropic in 2024, it defines how AI models discover and invoke tools, resources, and prompts natively — no spec-reading or prompt engineering required.
12
MCP and OAS operate at different layers. OAS solves "what can this API do?" at build time. MCP solves "how does an AI invoke it?" at runtime. The Connector sits between them — it internalises the spec so the LLM never has to read it.
13
Claude treats MCP tool selection like a search problem. Tool descriptions are the ranking signal, explicit service mentions are hard overrides, and true ties are surfaced to the user. Write specific tool descriptions — vague ones lose in multi-MCP environments.
